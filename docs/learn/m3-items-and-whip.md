# M3 讲解：道具系统与藤鞭的三种用法

## 道具 = 动词，不是物品

道具系统的骨架小到只有一句话：按使用键时，按当前激活道具**分派一个动词**。世界（`world.useItem`）负责分派，玩家和实体负责响应。新增一件道具 = 加一个分派分支 + 若干实体响应，不用碰任何现有道具。

切换道具用 `cycle` 动作（L），HUD 左下角三个槽位图标常驻——玩家永远知道有什么、拿着什么，全程无需文字。

## 藤鞭的三种用法，一个判定盒

挥鞭产生一个临时判定盒 `whipBox()`（面朝方向 14×10px，只在挥动前 65% 时间有效）。三种用法共享它：

1. **砍藤**：`VineBud.update` 发现判定盒与自己相交 → 移除自己、粒子飞溅
2. **打机关**：`Switch` 同样的相交检测 → 置 flag、开门
3. **荡钩环**：这是唯一不走判定盒的——在使用瞬间，先扫描**附近且在头顶方向**的钩环，够到就直接进入摆荡（`attachSwing`），根本不产生挥鞭动画

**一次挥击只命中一个目标**：`whipId` 自增 + `whipConsumed` 集合去重。不然一鞭扫过两个藤蔓会连环消耗，判定"划算"得让玩家困惑。

## 摆荡：八行单摆

```
ω += -(g/L)·sin(θ)·dt      // 重力对摆的回复力
θ += ω·dt
位置 = 钩环 + (L·sinθ, L·cosθ)
```

接入现有物理的关键只有两处：

- **起摆**：把玩家当时的水平速度投影成角速度 `ω = vx·cosθ/L`——跑跳上钩会自然荡起来，静止起钩就直垂
- **脱摆**：按跳跃时把角速度还原成切向速度 `v = ωL·(cosθ, -sinθ)`，再给一点向上奖励。荡到最高点脱手能"甩"出去，这是整个机制爽感的来源

空中按 A/D 还能给 ±角加速度（泵摆），高手可以荡得比初始动量更高——深度的来源，但完全不用解释。

## 蓄力伸长与锁定拉拽

最初的设计是"按下 K 的瞬间，近距离钩环直接 attachment"——近的顺手，远的够不着，中间地带（恰好差 10px）最挫败。重做后的模型：

- **按住 K 蓄力**：鞭尖随蓄力伸长（14 → 32px），索距同步扩大（28 → 48px）
- **锁定**：蓄力中每步扫描射程内的钩环，命中即进入**拉拽**——角色以 240px/s 被拖向钩环
- **起摆**：拉到环下时，沿接近方向给固定初速（2.2 rad/s）接标准摆荡——摆荡的长度与手感蓄力前后完全一致

实现上的两个坑，都是"状态没跟上视觉"：

1. **摆荡从未更新 `vy`**。位置每帧从单摆方程算，但 `player.vy` 永远是 0——而摆荡中的 vy 是"什么时候松手会往下掉"的真实状态，测试读它、泡泡载人读它。教训：**派生状态（速度=位置的导数）也要保持一致，否则所有依赖它的判断都在盲飞**。
2. **恒定力矩不是泵摆**。按住方向给恒定角加速度，只会让秋千微微歪向一边（3°），幅度永不放大。正确的泵摆只在**顺摆方向**做功（`ω·pump > 0` 才加力）——共振放大，越荡越高。物理直觉直接决定手感。

## flag：谜题状态的唯一事实源

机关/门/藤蔓/花苞的状态全部存在 `world.flags`（字符串集合，如 `door:11`、`vinebud:1,1#0`）。实体自身不保存状态，每帧从 flags 读取。好处：存档 = 序列化一个 Set；读档 = 重建房间时按 flag 摆好实体。**没有第二份需要同步的状态，就不会有状态漂移。**

## 教训：判定盒要"够得着玩家想打的东西"

藤蔓厅的藤墙最初从第 9 行垂到第 12 行，底缘恰好比玩家站立挥鞭的判定盒高出 1px——**永远砍不到，主路径死锁**。砍藤测试抓到后，把藤墙下移一行解决。规则：

- 需要"站在平地上就能交互"的物件，其可交互面必须延伸到**地面高度**
- 改完判定相关的任何东西，重跑一遍交互测试（`scripts/` 里的脚本就是干这个的）

## v3：螺旋扫击——"蓄力"为何被删掉

第五轮反馈把藤鞭从"短促抽打 + 按住蓄力锁钩环"改成了**螺旋扫击**：按一下 K，鞭子前 22% 进度甩满长度（160px，320×180 的屏幕上约等于满屏），之后全长转一整圈——边变长边做圆周运动的"甩螺旋"。**蓄力机制整个删掉了**，因为满屏扫击把"够不够得着钩环"的问题彻底消灭，蓄力唯一存在的意义（扩大索距）随之消失——当新机制覆盖旧机制的存在理由时，旧机制就该删，而不是留着一堆兼容分支。

三个值得记住的实现决策：

1. **"经过"必须是连续的，不能按帧采样**。转速约 1000°/s，一个逻辑步转 ~17°——在 150px 半径处，两帧之间鞭身会离开节点 20+px，按帧判定必然漏检。解法：把这一步扫过的扇面切成转角 ≤0.08rad 的小线段（`whipPrevE` 记录上一步扫到哪，下一步续扫），每段都做线段-点 / 线段-矩形检测。**高速运动的判定要扫过"扫过的面积"，不是抽查瞬间位置**。
2. **所见即所得**。鞭身画到哪，判定就在哪（`whipSegs` 同时喂渲染和判定），不存在"看着没碰到却判定命中"。旧的 whipBox 是一个朝向矩形，和转圈的视觉天然打架——删掉。
3. **满屏射程必须配隔墙检测**。射程 14px 时隔墙命中不可能发生；射程 160px 后鞭子能隔两格岩壁打中机关、钩住背后的钩环。给挂钩和打击都加了 5px 步进的视线采样（`lineBlocked`）——**射程每放大一档，就重新审视一遍"原来不可能的 bug 现在可能了吗"**。

可读性（用户原话："速度可以快一点，但是不能看不清"）靠三件事：转速末端缓出减速、两道残影表达运动方向、鞭梢自带一小圈光——暗井里转多快都看得见它在哪。

## v3.1：按住一直转 + "永远有响应"的泵摆

用户实测后把 v3 的"按一下转一圈"改成了**按住持续旋转**：鞭长 3 秒内从 10px **线性**长到屏宽一半（160px）并保持，松手即收、再按从初始长度重长。实现上最重要的改动是把 `whipT` 的语义从"倒计时"换成"已旋转秒数"——第一版直接翻车：顶部的通用计时器块还在每步 `whipT -= dt`，把按住时的 `+= dt` 精确抵消，鞭长永远停在初始值。**一个字段只能有一个所有者；把倒计时字段改成语义相反的累计字段时，先全局搜它的衰减行。**

泵摆那半句用户原话是"摇摆的时候依旧不能通过左右交互增加水平动量"——按 bug 报告处理。旧实现只在"输入方向与当前摆向同号"时做功（纯共振泵），玩家按错半拍就毫无反馈，体感就是"没用"。改成**永远有响应**：顺摆向 +4.5/s（共振放大，每 0.1s 冒一粒尘让它"看得见加到力了"），反摆向 −1.5/s（物理上是刹车，也给了玩家杀速度的手段）。然后测试脚本本身也换成"左右交互"——按 ω 的符号实时换边按键（不再是无脑按住 D），照样荡过尖刺坑。**给手感机制配反馈，让玩家分得清"机制没触发"和"我按错了"。**

## v3.2：链摆三课（**本节改动已整体回退**——用户实测原版手感可接受，以下保留为设计记录）

> 回退范围：点按冲量、双向泵摆刹车、脱手冲量上调、动量起摆、脱手环免疫、WHIP_START_LEN 28。保留：第三环/四环关卡布局、右台西扩、按住 K 持续旋转（v3.1）。

## v3.2：链摆三课——"流畅"是被测出来的

荡索室改成三连环（8/11/18）让玩家"连续钩住过坑"，为此连修四处手感根基，每一处都是链摆测试红着暴露的：

1. **起摆方向要跟动量，不要跟几何。** 旧 `pullDir = sign(环.x - 人.x)`（环在人哪边就往哪摆）——链摆时人明明向右飞、抓的是右前方的环，却因为判定瞬间人还在环左侧而**向左起摆**（荡回去）。改成 `sign(抓环瞬间的 vx)`：向哪飞就向哪荡，落单静抓才回退到几何判定。**运动类状态的"方向"应该来自动量，不来自静态方位。**
2. **刚脱手的环要短暂免疫。** 脱手后重旋，鞭子的第一扫总会扫过身后的旧环（它最近）——旧环被立刻抓回来，链摆永远出不了第一环。加 0.6s 免疫窗（只对"刚脱手的那一环"）。**"不许立刻反悔"是让动作系统向前流动的必要规则。**
3. **脱手冲量要按目标距离给。** vx ×1.3/上抛 −30 的弧线在 980px/s² 的重力下只够飞 30px——三环链距 30~70px，第二环永远差一口气。上调到 ×1.4/−40 后弧线覆盖 50~90px。**抛物线手感的账要拿重力常数算，不要拍脑袋。**
4. **测试脚本别用外部短周期轮询拖垮游戏。** 无头浏览器里每次 `evaluate` 往返可长达数百 ms，30ms 轮询会把 rAF 循环拖到 5% 速度（游戏"卡"得泵摆永远起不来）。改用 `waitForFunction`（页内逐帧轮询，零 CDP 开销）等脱手窗口，瞬时条件也能稳定捕捉。

另：WHIP_START_LEN 10→28——初始鞭长太短的话，重旋后的第一扫够不到任何环，"救援窗口"（脱手到坠坑之间）根本不存在。
